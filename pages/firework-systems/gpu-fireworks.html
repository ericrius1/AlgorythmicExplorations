Firework Systems · Part 1

Fireworks at GPU Scale

A fireworks show where the CPU only describes each launch and the GPU creates, moves and draws every spark. The sky above is running live.

Scroll down to read ↓

Fireworks make a good stress test because every piece is cheap and there are suddenly a lot of pieces. A rocket is one particle, and its trail is a few hundred more. The shell it bursts into is a few thousand. Hold the mouse down in the last figure on this page with the spark count turned up, and that turns into millions of particles a second.

The obvious first design is a big ring buffer. Launching a firework means the CPU writes particle records into the ring, old ones expire by timestamp, and the renderer draws the part of the ring that has been used. That works until you push it. Then newer sparks lap the ring and older ones vanish in mid-air. Or the sky goes dark while the CPU's bookkeeping still says hundreds of thousands of particles are alive, because its idea of what's alive and what the GPU is drawing have drifted apart.

A bigger ring, or a reserve buffer for emergencies, only moves the problem. What fixed it was taking individual particles away from the CPU. The CPU says what to launch. Creating the sparks, ageing them, deciding which are still alive and counting them for the draw call all happen on the GPU.

It's the same shape as the accretion demo in Particle Worlds part four: long-lived GPU buffers, a fixed list of passes, small parameter writes from the CPU, and a renderer that draws whatever the simulation just wrote. The physics here is much simpler. The plumbing is the interesting part.

Step 1 · EventsSend the recipe, not the sparks

Nobody launches 50,000 particles. You launch a firework, and the firework happens to contain 50,000 sparks. If the CPU uploads one record per spark, it's working at the wrong level. So it uploads an emit command instead, one small struct per event: 

struct EmitCommand {
  header:       vec4u,  // kind, count, start, aux
  posScaleSeed: vec4f,  // origin, size scale, random seed
  velLifeSize:  vec4f,  // velocity or burst speed, then per-kind counts and times
  color:        vec4f,
  accent:       vec4f,
  homeParams:   vec4f,  // burst centre, depth, one more per-kind number
}

A rocket command makes one particle. A trail command makes six sparks and puffs of smoke behind the rocket, and the rocket sends one every 18 milliseconds of its flight. An explosion command makes the whole shell: a centre flash, the main sparks, crackle, falling embers and smoke. The command holds the recipe, not the particles.

On the GPU, one thread runs for every particle to be created this frame. Each command records where its particles start in that frame's list, so a thread finds its command with a binary search, works out its index inside it, hashes the command's seed with that index, and fills in a particle record from the result.

A particle here is 80 bytes: position, velocity, colour, age, lifetime, size, kind, seed, shell level, depth, and the centre of the burst it belongs to. A command is 96 bytes. One shell of 50,000 sparks is about 3.8 MiB of particle records, or a single command. The figure counts the flash, crackle, embers and smoke as well, and even with both sliders all the way down the commands are more than 500 times smaller.

The GPU still creates every particle and writes every record. That work just happens in parallel, right next to the buffer it goes into, and the CPU stays at the level of the interaction: a pointer down, a target, a colour, a spark count.

Aside · Particles were invented for fire

The term comes from William Reeves at Lucasfilm, who built the wall of fire that spreads across a planet in the Genesis sequence of Star Trek II (1982) and described it in a 1983 paper. His particles had a position, velocity, size, colour, transparency and lifetime, and each was created from a few random draws around averages the animator chose. That's the record in this renderer, plus a depth. Twenty years later Lutz Latta's "Building a Million Particle System" moved the state into GPU memory and updated it there, which is the idea this page runs on.

Step 2 · CompactionA list that cleans itself up

With emission on the GPU there's no CPU particle array left: no expiry times, and no high-water mark guessing how much of a ring is worth drawing. There are two particle buffers on the GPU, and each frame one is read and the other is written. simulateCompact runs one thread per particle in last frame's list. Each thread moves its particle forward a step, and if it's still alive, appends it to the other buffer. Then emitParticles appends this frame's new particles after the survivors. Next frame the two buffers swap.

It's the ping-pong pattern from fluid solvers and cellular automata, and the written list is always dense. A spark that dies just doesn't get appended, so there's no hole to fill and nothing to clear.

The compaction pass, as it is in the shader:

@compute @workgroup_size(256)
fn simulateCompact(@builtin(global_invocation_id) gid: vec3u) {
  let i = gid.x;
  let activeCount = atomicLoad(&counters.live);
  if (i >= activeCount) { return; }

  let p = simulate_particle(particlesIn[i]);
  if (p.ageLife.x >= p.ageLife.y || p.ageLife.y <= 0.0) { return; }  // expired
  append_particle(p);
}

fn append_particle(p: Particle) {
  let outIndex = atomicAdd(&counters.write, 1u);  // claim the next free slot
  write_particle(outIndex, p);
}

The atomicAdd is what keeps the list dense. Every surviving thread claims the next free slot, and no thread needs to know where the others went. Two things follow from that. The order isn't kept: slots go out in whatever order the threads reach the atomic, so a particle can land ahead of one that was before it, as in the figure. That's fine here because every particle is drawn with additive blending, and adding up light gives the same total in any order.

And the count is exact. When a 50,000-spark shell is down to its last 12,000, the write counter says 12,000, because that's how many appends happened. When the last spark dies, the next frame appends nothing and the count is zero. The renderer and the debug readout are looking at the same number.

Step 3 · IndirectThe GPU fills in the draw call

If the CPU doesn't know how many particles survived, how does it draw them? It doesn't have to know. The GPU writes the draw call's arguments as well. Each particle is a billboard of six vertices, two triangles stretched along its velocity, and WebGPU's drawIndirect reads its four arguments from a buffer: 

drawArgs.vertexCount   = 6
drawArgs.instanceCount = live      // written on the GPU
drawArgs.firstVertex   = 0
drawArgs.firstInstance = 0

A one-thread pass, finishFrame, writes those after simulation and emission are done, and the render pass calls drawIndirect(drawArgs). The CPU never reads the count back or waits for it. It records the same command every frame, and the GPU fills in the number before the draw runs.

finishFrame also writes next frame's dispatch size for the simulation, ceil(live / 256) workgroups, into a second indirect buffer, so the simulation only runs threads for particles that exist. The buffers have room for 1.7 million particles each, but an empty sky dispatches zero simulation workgroups, emits nothing, and draws zero instances.

The whole frame is one short command buffer:

beginFrame       // zero the write counter and the draw count
simulateCompact  // indirect: one thread per particle alive last frame
emitParticles    // one thread per new particle
finishFrame      // live = write; draw args; next frame's dispatch size
drawScene        // the backdrop
drawIndirect     // the particle list, with finishFrame's instance count

The order matters. New particles go in after the survivors, so a particle emitted this frame is drawn this frame. The emit dispatch is the only one sized on the CPU, which is fine, because the CPU wrote the commands and already knows how many particles they make.

Aside · Where indirect draws came from

Draw calls whose arguments live in GPU memory arrived with Direct3D 11 in 2009 and OpenGL 4.0 in 2010. Direct3D 11 also turned the atomic-append pattern above into a buffer type, AppendStructuredBuffer. WebGPU has no append buffer, so here it's an atomic counter and a plain array, which is what an append buffer is underneath.

Step 4 · LimitsCapacity comes from the device

Taking out the arbitrary limits doesn't mean pretending the hardware has none. It means telling a policy apart from a fact. "Never let more than 150,000 particles exist, in case it's slow" is a policy. "This device allows 128 MiB in one storage buffer binding" is a fact, and the particle capacity falls straight out of it: 

capacity = floor(device.limits.maxStorageBufferBindingSize / 80)

This page asks WebGPU for a device with the default limits, so the binding limit is 128 MiB and the capacity is 1,677,721 particles per buffer on every machine. Most GPUs would grant a much bigger binding if the page asked for one with requiredLimits, and the figure reads what yours would allow. There are two particle buffers, because compaction reads one while it writes the other, so the particles take 256 MiB. The emit command buffer adds 6 MiB, room for 65,536 commands in a frame (it doubles if a frame needs more), and the counters and indirect arguments add a few dozen bytes.

When more particles are asked for than fit, write_particle skips the write and counts it instead. Nothing older is erased to make room and there's no hidden reserve: 

fn write_particle(index: u32, p: Particle) {
  let capacity = arrayLength(&particlesOut);
  if (index < capacity) {
    particlesOut[index] = p;
  } else {
    atomicAdd(&counters.overflow, 1u);  // never reset, so no readback misses one
  }
}

Survivors are appended before new particles, and there can never be more survivors than the buffer holds, so when a frame overflows it's always the newest particles that get dropped. Sparks already in the sky never disappear to make room.

Aside · There's no memory budget to ask for

Browsers don't expose a portable "total memory this page may use" number. WebGPU gives you limits, like the largest storage buffer binding, and you know your own allocations. So those are the two numbers worth showing: the biggest legal particle buffer, and what the effect has actually reserved.

Step 5 · PhysicsCheap because it's local

None of this makes the particles look simple. Each one has a kind (rocket, spark, ember or smoke) and each kind gets its own acceleration, drag, size, colour and lifetime. Rockets feel 13% of normal gravity and reach their target in 0.7 to 0.9 seconds. Sparks fall and swirl. Embers start out slower, drop, and last 1.1 to 2.7 seconds. Smoke drifts upward.

The swirl comes from a cheap procedural field. The sky is cut into a grid 18 cells across, each cell points in a random direction that changes about once a second, and there's a spin around each cell's centre on top. It isn't a fluid solve, or even proper curl noise like the fluid instrument uses, but what the eye wants is sparks that curl, and this is a few lines of arithmetic per particle.

Every fourth volley the hero fires a different kind of shell. Its grains fly out like a normal burst, then about 0.9 seconds later a spring pulls them back toward the centre. A hash of each grain's grid cell staggers when it starts to pull, so the collapse ripples inward instead of snapping shut. It's a nod to the dust clumping in part four of Particle Worlds; nothing actually collides.

Drawing is where the physics becomes readable. Each particle is stretched along its velocity, so fast sparks become streaks and slow smoke stays round. The painted backdrop comes with a depth map, and a particle fades out wherever a ridge is nearer than it is, so falling sparks drop behind the mountains and rockets rise out from behind them. Everything is added into a floating-point target, so overlapping sparks keep adding up, and then gets bloom and filmic tone mapping, the same finish as the Particle Worlds demos.

What makes the high counts possible is that the update is local. A particle never looks for neighbours, sorts into a grid or walks a tree. It reads its own record and a few uniforms, and writes one particle or none.

Step 6 · LayoutName the bytes

The least glamorous habit here turned out to be the most useful: give every storage layout a name. It's tempting to treat the counters as a bare array of u32 and remember that counters[0] is the live count and counters[4] the overflow. A struct puts that contract in the shader: 

struct Counters {
  live:         atomic<u32>,
  write:        atomic<u32>,
  commandCount: atomic<u32>,
  totalEmit:    atomic<u32>,
  overflow:     atomic<u32>,
  pad0: atomic<u32>, pad1: atomic<u32>, pad2: atomic<u32>,  // 32 bytes
}

The CPU still writes words at byte offsets (commandCount and totalEmit go in at byte 8 every frame), but the shader says what each word means, and "which counter was index 3?" stops being a question.

Names come with one surprise. WGSL reserves a long list of words from other languages, and active and target are both on it. A shader that uses one as a field name fails when the module compiles, and if nothing checks, all you see afterwards is a stream of "invalid pipeline" errors, one per frame. So every module and pipeline gets a label, every module's compilation messages get logged, and every pipeline is created inside an error scope: 

const module = device.createShaderModule({ label: "firework sim", code });
module.getCompilationInfo().then(logMessages);  // line, column, message

device.pushErrorScope("validation");
const pipeline = device.createComputePipeline({ label, layout: "auto", compute: { module, entryPoint } });
device.popErrorScope().then((error) => {
  if (error) console.error(`${label} validation: ${error.message}`);
});

None of that is about fireworks. It's the WebGPU habit that pays for itself first: the real error shows up once, with a name on it, instead of a flood of symptoms a few frames later.

Step 7 · DiagnosticsRead back less than you want

The counters make the cheapest possible debug overlay. Four times a second, the frame that just ran copies the 32-byte counter buffer into a buffer the CPU can map, and mapAsync hands the numbers over a frame or two later. The simulation never waits for them. Copying the particle buffer back to count particles would move 128 MiB to learn one number.

Here's the real thing with those counters showing. It shares its buffers with the hero at the top of the page, so the page only allocates them once. Press and hold on the sky to launch; while you hold, it fires eight launches every half second. Then turn sparks per shell up to 100,000, set twelve rockets per launch, and hold again. Within a second or two the live count runs into the capacity, and the overflow total starts climbing by tens of millions a second. Let go and the live count drains back down as the sparks burn out (switch auto off to watch it reach zero).

The live count and the overflow total come off the GPU. The emitted counts are the CPU's, since it wrote the commands that asked for those particles. Watch the frame rate while the buffer is full. Whether the time goes to emission, compaction or filling pixels with 1.7 million billboards is the next thing I'd measure.

EpilogueWhat carries over

  • Send events, not data. One command per launch, expanded on the GPU next to the buffer the particles live in.
  • Let the GPU count. The write counter is the live count, the draw count and next frame's dispatch size, so nothing has to estimate it.
  • Keep limits and policy apart. Capacity comes from the device, and when it runs out the overflow is counted where you can see it.
  • Read back counters, not particles. Thirty-two bytes four times a second is enough to debug the whole system.

Things I'd try next: let compute passes write emit commands too, so the follow-up pops around each shell, which the CPU still schedules, become GPU state as well. Time each pass with timestamp queries, to see whether a slow frame at a million particles is emission, compaction or fill rate. And draw the smoke with ordinary alpha blending so it can darken the sky, which would mean sorting just the smoke. The command idea also reaches well past fireworks: fountains, sparks off collisions, rain splashes, dust kicked up off terrain. If an event fits in a few numbers and can be expanded procedurally, the CPU should send the event.
