Firework Systems · Part 1

Fireworks at GPU Scale

How to run a million-spark fireworks show in WebGPU by moving emission, compaction, and draw-call sizing off the CPU.

Scroll down to read ↓

If you build a fireworks demo with a standard CPU ring buffer, everything behaves politely right up until you hold the mouse button down. A single rocket is cheap, its trail adds a few hundred particles, and its burst drops a few thousand more into the sky. Crank the spark count up and launch a heavy volley, though, and the ring starts wrapping around on itself: fresh sparks overwrite older bursts still hanging in mid-air, so whole shells blink out of existence. Worse, once timestamps and high-water marks drift out of sync with what the GPU actually rendered, you can stare at an empty night sky while the CPU's counter insists 400,000 sparks are still alive.

Allocating a bigger ring or bolting on an overflow pool only delays that breakdown. The cleaner architectural move is to stop tracking individual particles on the CPU altogether. The CPU stays in charge of high-level events (where a rocket launches, when a shell pops, what palette it uses), and the GPU handles everything per particle: spawning sparks, aging them, dropping dead ones, and telling the render pass exactly how many billboards to draw.

Structurally, this ends up looking a lot like the accretion simulation in Particle Worlds part four: persistent GPU buffers, a predictable chain of compute passes, tiny per-frame uploads from JavaScript, and a renderer that consumes whatever the simulation just wrote. Compared to gravity and collisions, firework physics is pretty forgiving, so almost all the interesting engineering here lives in the data flow.

Step 1 · EventsUpload launch recipes

When a shell explodes into 50,000 sparks, pushing 50,000 initialized particle structs across the bus from JavaScript wastes both CPU time and PCIe bandwidth. Instead, the CPU writes a single 96-byte emit command describing the event: 

struct EmitCommand {
  header:       vec4u,  // kind, count, start, aux
  posScaleSeed: vec4f,  // origin, size scale, random seed
  velLifeSize:  vec4f,  // velocity or burst speed, then per-kind counts and times
  color:        vec4f,
  accent:       vec4f,
  homeParams:   vec4f,  // burst center, depth, one more per-kind number
}

Every visual beat maps to one of these structs. A rocket launch queues a one-particle rocket command plus an initial puff, and as the rocket climbs, the CPU queues a six-particle trail command every 18 milliseconds. When the rocket reaches its apex, one explosion command encodes the entire shell: a bright center flash, the main sparks, crackle, falling embers, and drifting smoke.

On the GPU side, the emit compute pass launches one thread per new particle requested that frame. Each command stores its starting offset in the frame's total emission list, so every thread binary-searches the command array to locate its own command, computes its local particle index inside that command, hashes the command's seed with that index, and synthesizes the full particle record right inside GPU memory.

Each simulated particle takes 80 bytes: position, velocity, color, age, lifetime, size, particle kind, seed, shell level, depth, and the center of its parent burst. For a single 50,000-spark shell, uploading initialized particles directly means sending roughly 3.8 MiB from the CPU, compared to 96 bytes for one emit command. The comparison above includes the flash, crackle, embers, and smoke that ride along with every shell, and even at the lowest slider settings the command stream stays more than 500 times smaller.

Of course, the GPU still has to generate and store every single one of those 80-byte records. The payoff is where that work runs: massively in parallel, directly into VRAM, while JavaScript stays free to deal with pointer events, launch timing, and color palettes.

Aside · Particles were invented for fire

William Reeves coined the term "particle system" at Lucasfilm while building the wall of fire that sweeps across a planet in the Genesis sequence of Star Trek II (1982), and laid out the technique in his 1983 SIGGRAPH paper. Each of his particles carried position, velocity, size, color, transparency, and lifetime, initialized from random variations around animator parameters. Aside from a depth value, our 80-byte record is practically identical. Two decades later, Lutz Latta's "Building a Million Particle System" shifted the entire particle state into GPU memory so simulation and rendering never had to round-trip through the CPU, which is the direct ancestor of the pipeline here.

Step 2 · CompactionA dense ping-pong list

Once emission moves to the GPU, the CPU stops keeping a shadow particle array at all. There are no CPU expiration timers and no guesses about how much of a ring buffer is currently populated. Instead, the GPU allocates two identical particle buffers and alternates between them every frame: one serves as the read-only input from last frame, and the other receives this frame's output. First, simulateCompact dispatches one thread per particle that survived last frame, integrates its motion, and appends it to the output buffer only if it is still alive. Right after that, emitParticles appends all freshly spawned particles to the tail of the same output buffer. On the next frame, the two buffers swap roles.

If you have written a fluid solver or a cellular automaton, you already recognize this ping-pong layout. The nice side effect for particles is that the active list stays tightly packed from index zero upward on every single frame. Expired sparks simply return early and never get written, leaving zero gaps to track or scrub.

The compaction kernel itself is surprisingly short:

@compute @workgroup_size(256)
fn simulateCompact(@builtin(global_invocation_id) gid: vec3u) {
  let i = gid.x;
  let activeCount = atomicLoad(&counters.live);
  if (i >= activeCount) { return; }

  let p = simulate_particle(particlesIn[i]);
  if (p.ageLife.x >= p.ageLife.y || p.ageLife.y <= 0.0) { return; }  // expired
  append_particle(p);
}

fn append_particle(p: Particle) {
  let outIndex = atomicAdd(&counters.write, 1u);  // claim the next free slot
  write_particle(outIndex, p);
}

That single atomicAdd on counters.write handles all the packing. Every surviving thread grabs the next consecutive index with no coordination across workgroups. That does scramble particle order from frame to frame, since threads reach the atomic counter in whatever order the GPU schedules them (you can watch blocks cross paths as they move between buffers above). Because the fireworks render with additive blending, order makes no difference: summing light is commutative.

You also get an exact headcount for free. When a 50,000-spark burst has burned down to 12,000 embers, counters.write equals 12,000 because literally 12,000 appends occurred. Once the final spark fades out, the next frame writes nothing and the live count drops cleanly to zero. Both the renderer and the diagnostics panel read that exact same integer.

Step 3 · IndirectLetting the GPU size its own passes

Because the live count lives strictly on the GPU, the CPU never knows how many particles survived compaction. Fortunately, WebGPU doesn't need the CPU to know. Each particle renders as an instanced six-vertex quad stretched along its velocity vector, and drawIndirect pulls its four draw parameters directly from a small GPU buffer: 

drawArgs.vertexCount   = 6
drawArgs.instanceCount = live      // written on the GPU
drawArgs.firstVertex   = 0
drawArgs.firstInstance = 0

After simulation and emission finish, a single-thread compute pass called finishFrame copies the final write count into drawArgs.instanceCount, and the subsequent render pass simply invokes drawIndirect(drawArgs). JavaScript submits the exact same command sequence every frame without ever stalling to read a number back.

finishFrame also populates a second indirect buffer with ceil(live / 256) workgroups for next frame's simulateCompact pass. Even though each particle buffer can hold nearly 1.7 million entries, an idle night sky dispatches zero simulation workgroups, emits zero particles, and draws zero instances.

Put together, an entire frame fits into one compact command encoder:

beginFrame       // clear the write counter and draw count
simulateCompact  // indirect: one thread per particle alive last frame
emitParticles    // one thread per newly emitted particle
finishFrame      // live = write; write draw args and next frame's dispatch size
drawScene        // painted backdrop and ridges
drawIndirect     // compacted particle list, sized by finishFrame

Running emitParticles after simulateCompact ensures newly created sparks appear on the very frame they were requested, right behind the survivors in the output buffer. The emit pass is the only dispatch whose workgroup count is computed on the CPU, which costs nothing because the CPU just packed those emit commands and already has the sum in hand.

Aside · Where indirect draws came from

GPU-populated draw arguments first landed in mainstream APIs with Direct3D 11 in 2009 and OpenGL 4.0 in 2010. Direct3D 11 also packaged the atomic-append pattern as a dedicated resource type called AppendStructuredBuffer. WebGPU leaves that abstraction out, so we build it from a raw storage buffer paired with an atomic counter, which is all an append buffer ever was in the first place.

Step 4 · LimitsDeriving capacity from the device

Most particle demos hardcode a safe ceiling like "max 150,000 particles" so nobody accidentally melts a laptop. That mixes a tuning preference with a hardware boundary. What the hardware actually enforces is the maximum size of a single storage buffer binding, and our per-buffer particle capacity falls directly out of dividing that limit by our 80-byte stride: 

capacity = floor(device.limits.maxStorageBufferBindingSize / 80)

Because this page requests a WebGPU device with default limits, every browser gives us a 128 MiB storage binding, which works out to 1,677,721 particles per buffer. Most desktop GPUs will happily grant much larger bindings if you request them via requiredLimits, and the diagram below queries your adapter to show what it would allow. With two ping-pong buffers, particle storage takes 256 MiB. The emit command buffer adds 6 MiB up front (65,536 commands per frame, doubling on demand if a frame somehow exceeds that), while the counters and indirect argument buffers add only a few dozen bytes.

If a massive barrage asks for more particles than fit, write_particle refuses to corrupt memory or overwrite existing sparks. It drops the extra write and bumps a monotonic overflow counter so the drop is immediately visible: 

fn write_particle(index: u32, p: Particle) {
  let capacity = arrayLength(&particlesOut);
  if (index < capacity) {
    particlesOut[index] = p;
  } else {
    atomicAdd(&counters.overflow, 1u);  // never cleared, so readbacks never miss a spike
  }
}

Because surviving particles always append before newly emitted ones, and the previous frame could never hold more survivors than the buffer's capacity, any overflow strictly trims brand-new particles. Bursts already blooming in the sky stay intact until they naturally burn out.

Aside · Why there is no memory-budget slider

Web browsers intentionally avoid exposing a portable "total VRAM available to this tab" API. WebGPU hands you concrete binding limits, and your own code knows exactly how many bytes it allocated, so those are the two honest numbers to surface: the largest legal particle buffer and the total VRAM the effect actually claimed.

Step 5 · PhysicsKeeping the update strictly local

Even with zero particle-to-particle interaction, you can get a lot of visual variety just by differentiating particle kinds. Every record carries a kind tag (rocket, spark, ember, or smoke) that selects its gravity, drag, size curve, color ramp, and lifespan. Rockets feel only 13% of spark gravity so they arc smoothly to their target in roughly 0.6 to 0.9 seconds depending on altitude. Sparks fan out, slow under air drag, and curl through the night air; heavier embers fall slower and linger for 1.1 to 2.7 seconds; smoke drifts gently upward.

To give sparks some organic curl without running a fluid simulation or full curl noise (like the fluid instrument does), the shader tiles the sky into an 18-cell procedural grid. Each cell assigns a random push that cross-fades about once a second, layered with a small swirl around the cell's center. Physically it is a total cheat, yet it takes only a handful of ALU ops per particle and reads convincingly as air turbulence.

Every fourth volley in the hero fires an alternate shell type called collapse. Its grains burst outward normally, hang for about 0.9 seconds, and then feel a spring pulling them back toward the shell's origin. A hash of each grain's spatial cell staggers when the pull kicks in, creating an inward ripple instead of a simultaneous snap. It echoes the gravitational clumping in Particle Worlds part four, achieved purely through per-particle math.

Rendering does the rest of the visual heavy lifting. Each billboard elongates along its velocity vector so fast sparks streak across the sky while lazy smoke puffs stay round. The painted mountain backdrop includes a matching depth texture; the particle fragment shader softens and fades any spark sitting behind a nearer ridge, so rockets climb from behind the hills and dying embers drop cleanly out of sight behind them. All particles accumulate into a floating-point HDR buffer with additive blending, followed by bloom and filmic tone mapping.

The reason this scales comfortably past a million particles is locality: a thread never searches for neighbors, sorts into buckets, or traverses a hierarchy. It reads one 80-byte struct plus uniforms, does a bit of arithmetic, and either writes one struct back or exits.

Step 6 · LayoutGiving the bytes real names

One small habit saved hours of debugging while building this: defining explicit WGSL structs for every storage buffer instead of indexing raw u32 arrays. Guessing whether counters[4] meant overflow or command count gets old fast, whereas a named struct puts the memory contract directly in the shader source: 

struct Counters {
  live:         atomic<u32>,
  write:        atomic<u32>,
  commandCount: atomic<u32>,
  totalEmit:    atomic<u32>,
  overflow:     atomic<u32>,
  pad0: atomic<u32>, pad1: atomic<u32>, pad2: atomic<u32>,  // 32 bytes
}

JavaScript still writes commandCount and totalEmit at byte offset 8 each frame, yet having named fields on the WGSL side catches mismatch bugs immediately and makes every compute kernel readable six months later.

Naming structs in WGSL comes with one classic gotcha: the spec reserves a large block of identifiers borrowed from other languages, including everyday words like active and target. Use one as a struct member and the shader silently fails compilation; if you don't inspect compilation info, the console just floods with unhelpful "invalid pipeline" validation messages every animation frame. Labeling every shader and pipeline, dumping compilation messages, and wrapping pipeline creation in a validation error scope surfaces the actual typo once, with line and column numbers: 

const module = device.createShaderModule({ label: "firework sim", code });
module.getCompilationInfo().then(logMessages);  // line, column, message

device.pushErrorScope("validation");
const pipeline = device.createComputePipeline({ label, layout: "auto", compute: { module, entryPoint } });
device.popErrorScope().then((error) => {
  if (error) console.error(`${label} validation: ${error.message}`);
});

That tiny wrapper has nothing specific to fireworks, and it pays for itself the very first time you mistype a binding index or trip over a reserved keyword.

Step 7 · DiagnosticsReading back 32 bytes at a time

Those eight atomic integers also double as a virtually free telemetry feed. About four times a second, the encoder copies the 32-byte counter buffer into a MAP_READ staging buffer and calls mapAsync. The result arrives on the CPU a frame or two later without ever blocking the render loop. Compare that to downloading a 128 MiB particle buffer just to count active entries.

To see the hard buffer cap in action, slide sparks per shell all the way to 100,000, turn rockets per launch up to 12, and hold on the sky: within a couple of seconds live particles pins against 1,677,721 and overflowed, total starts climbing in the millions. Release the pointer and toggle auto off to watch the active list compact itself cleanly back down to zero.

Notice which side owns which number: live particles and overflowed, total come straight back from the GPU counter buffer, whereas emitted, last second and emit commands, last second are tallied on the CPU as commands are queued. Try switching shell: classic to shell: collapse while watching the frame rate near full capacity; at 1.7 million glowing quads, overdraw and pixel fill rate start competing directly with compute time.

EpilogueWhere this architecture goes next

Once you build a particle engine this way (compact event commands from JavaScript, ping-pong atomic compaction in compute, indirect draw and dispatch sizing, device-derived caps with visible overflow accounting, and tiny async counter readbacks), the CPU stops being a bottleneck altogether. The exact same plumbing applies well beyond fireworks: waterfall spray, sparks kicked off rigid-body impacts, rain splashes, or dust clouds behind wheels. Anytime an effect can be described by a handful of parameters and expanded procedurally, keeping the CPU at the event level keeps both code and bandwidth small.

If I keep pushing this renderer further, three experiments are right at the top of my list. First, letting a compute pass append new emit commands into a GPU-side queue would move the delayed satellite pops around each main shell off the CPU too, making multi-stage shells completely self-sustaining on the GPU. Second, wiring WebGPU timestamp queries around each pass would tell us cleanly whether a frame drop at 1.7 million particles is bound by emission, compaction, or sheer billboard fill rate. Finally, rendering smoke in a separate alpha-blended pass would let it occlude and darken the bright bursts behind it, though that immediately reintroduces sorting for the smoke slice alone.
