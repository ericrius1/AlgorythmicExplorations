Small Minds · Part 1

The Grid That Thinks

Before a single word is predicted, a language model is a memory-bandwidth puzzle solved in tiny 16×16 tiles of shared GPU silicon.

Scroll down to read ↓

Strip away the mystique around modern language models and you are left with a remarkably compact machine. Almost everything a Transformer does — projecting tokens into queries, keys, and values, routing concepts through gated feed-forward layers, predicting the next character, and sending gradients backward through time — boils down to one operation repeated hundreds of times per second: multiplying two dense grids of floating-point numbers.

In this five-part series, we are going to build an entire modern language model from raw metal inside your browser tab using pure WebGPU and hand-written WGSL compute shaders — no ML runtimes, no ONNX, no black boxes. We will start with matrix math and tokens here, build RoPE and FlashAttention in Part 2, wire up full GPU backpropagation in Part 3, turn your browser into an autonomous researcher that mutates and improves its own models in Part 4, and finally pour all of it into a living 3D companion that chats, plays, dreams, and grows with you across visits.

Step 1 · Hardware realityWhy GPUs wait on memory, not math

A modern laptop or phone GPU can perform trillions of floating-point multiply-adds every second, yet its main memory (VRAM or unified DRAM) can only feed a tiny fraction of those numbers across the wire each cycle. Computer architects call the ratio between math done and bytes moved arithmetic intensity.

When you write the textbook triple-loop matrix multiply in a compute shader — one thread per output element C[row, col], looping k = 0..K-1 — every fused multiply-add (2 FLOPs) reads two 4-byte floats (8 bytes) straight from global memory. That gives an arithmetic intensity of just 0.25 FLOP/byte. Your GPU's arithmetic units sit idle almost the entire time waiting for bytes to arrive. 

// Naive: every thread hits global DRAM 2·K times
for (var k = 0u; k < dims.K; k++) {
  acc = fma(A[row * dims.K + k], B[k * dims.N + col], acc);
}

Step 2 · Shared memorySixteen-by-sixteen cooperation

The trick that unlocks GPU speed is noticing that neighboring output cells need the exact same rows of A and columns of B. Instead of letting 256 threads fetch the same numbers independently from slow global memory, we group them into a 16 × 16 workgroup and give them two tiny scratchpads inside fast on-chip SRAM using WGSL's var<workgroup>. 

var<workgroup> tileA: array<f32, 256>;
var<workgroup> tileB: array<f32, 256>;

for (var t = 0u; t < numTiles; t++) {
  tileA[ly * 16u + lx] = A[row * K + t * 16u + lx];
  tileB[ly * 16u + lx] = B[(t * 16u + ly) * N + col];
  workgroupBarrier();
  for (var k = 0u; k < 16u; k++) {
    acc = fma(tileA[ly * 16u + k], tileB[k * 16u + lx], acc);
  }
  workgroupBarrier();
}

Each thread loads just one element of A and one element of B per tile, waits at workgroupBarrier(), and then performs 16 multiply-adds out of on-chip SRAM before touching main memory again. Global memory traffic instantly drops by 16×, pushing arithmetic intensity up to 4.0 FLOP/byte. Try pushing N up to 1024. At small sizes, dispatch overhead hides the gap; once matrices outgrow the L1 cache, the tiled kernel pulls dramatically ahead because its threads cooperate instead of competing for the memory bus. Every linear layer in our Transformer — forward projections (A @ Bᵀ), backward activation gradients (dY @ W), and weight gradients (dYᵀ @ X) — reuses this exact 16×16 workgroup-tiling engine.

Why three matmul layouts matter for backpropagation

A linear layer computes Y = X · Wᵀ where X is [N, D_in] and W is [D_out, D_in]. During the backward pass we need two different transposes without copying or transposing buffers in memory: dX = dY · W (standard tiled A @ B) and dW += dYᵀ · X (tiled Aᵀ @ B with an accumulate flag). Writing those three tiled entry points in matmul.wgsl eliminates every intermediate transpose kernel from our training step.

Step 3 · Words into vectorsTokenization and embeddings

Matrix multipliers only speak floats, so our first bridge from human language to silicon is twofold: slice text into integer IDs (tokenization), then look up each ID in a learned table of vectors W_E (embeddings).

Real frontier models use Byte-Pair Encoding (BPE): start with individual characters, count every adjacent pair in the text, merge the single most frequent pair into a new token ID, and repeat. Common words collapse into single integers while rare words fall back cleanly to pieces. For our interactive in-browser GPU trainer in Parts 3 through 5, we will use a crisp 98-token printable-ASCII vocabulary. That keeps the output softmax matrix tiny — [N, 98] instead of [N, 50257] — so a complete Transformer can train at hundreds of steps per second on your browser GPU while still spelling arbitrary English, punctuation, and code from scratch.
